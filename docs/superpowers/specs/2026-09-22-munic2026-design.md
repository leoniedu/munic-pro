# MUNIC 2026 — Collection Monitoring as a Browser Extension

**Date:** 2026-09-22
**Status:** Design approved, scoped to an MVP
**Supersedes:** `ibgeba.munic2025` (R package)
**Sister project:** `sigc-pro` (shares idioms, not code)

## Purpose

Monitor MUNIC 2026 data collection in Bahia: fetch collection status from
SIGC, keep a dated history, and present it as a report — replacing the 2025 R
package, which only its author can run.

## MVP scope

The colleague's machine has **Excel Online, not desktop Excel**, and Excel
Online cannot pivot a local CSV. The in-browser panel is therefore *the
report*, not a convenience — an "export and pivot it yourself" design would
leave the colleague with nothing usable.

**In scope:**

- fetch, parse, validate
- IndexedDB SCD type-2 history
- three-tab panel: Município, Assistência (with %), Agência (with %)
- auto-downloaded JSON snapshot each run (durability)
- two CSV exports — for the author's R analysis and LibreOffice, not for the
  colleague's daily use

**Deferred, not deleted:**

- `.xlsx` export (SheetJS) — the panel and CSV cover the need
- `AtualizarCriticas` trigger — off until its semantics are confirmed
- RCD 202531 reassignment and the assistência enrichment *if* the 2026
  response's own agência proves sufficient (see Enrichment)
- import/merge of snapshots from a second machine

## How this design arrived here

Two earlier designs were worked through and discarded. The reasoning is kept
because it explains why the extension route wins, and because both dead ends
are plausible enough to be re-proposed later.

**Draft 1 — portable Python + Playwright.** A vendored Python and Chromium on
the locked-down machine, driving a browser for login and scraping over HTTP.
Reviewed and found to rest on a false premise: it read cookies from the
Playwright profile's SQLite store, but Chromium encrypts cookies via
`components/os_crypt` on Windows (shared by every Chromium build, not just
branded Chrome), and session cookies — exactly the F5 `MRHSession` ones — are
deleted when a profile reloads. Fixable via `context.cookies()`, but the
design still carried ~200 MB of bundle, AppLocker risk, DPAPI exposure, F5
replay fragility and a Windows build box.

**Draft 2 — extension captures, local Python processes.** Removed the auth
problem but kept a two-part system and a `.bat`.

**This design.** The extension does everything. The decisive facts:

- The user's existing `sigc-pro` extension **already fetches SIGC report
  endpoints exactly this way** —
  `extension/features/ultimo-movimento-export/ultimo-movimento-export.js`
  loops agências, POSTs to `/relatorio/filtrar`, parses the HTML table with
  `DOMParser` and downloads a combined CSV. MUNIC's two endpoints are simpler
  than what that file already handles.
- That feature **replaced a standalone `ultimo_movimento.py`** (its header
  comment says so). This exact migration has been made before, successfully.
- Running inside the authenticated browser **deletes the entire auth
  problem**: no cookie extraction, no DPAPI, no F5 session replay, no
  Playwright, no session-expiry handling. `credentials: 'same-origin'` carries
  the session.

Removed from scope by this decision: Playwright, portable Python, the ~200 MB
bundle, DuckDB, the `.bat`, the Windows build box, AppLocker risk, and every
pre-build verification item about executing binaries on the target machine.

## Relationship to sigc-pro

**A sister extension, not a feature of `sigc-pro`.**

`sigc-pro` guarantees *"Nenhum dado do SIGC sai do seu computador"*, ships
with an empty `permissions` list, and enforces this with a pre-commit hook and
CI gate that **ban `chrome.storage` globally** (`README.md:183-190`). MUNIC
history requires persistent storage.

Folding MUNIC in would mean breaking that gate and rewriting the privacy
claim — the extension's strongest asset — for an unrelated survey. The
guarantee would become "except for MUNIC history".

So: a separate extension with its own manifest, its own storage permission and
its own honest privacy text. `sigc-pro`'s guarantee stays absolute.

**Code is shared by copying**, not by a package. `sigc-pro` has almost no
build step, and adding one to serve two projects costs more than the
duplication. Copied from `extension/common/sigc-common.js`: `f5Prefix()`,
`fetchViaGateway()`, `downloadFile()`, `normalizeLabel()`, and the button
factories. Divergence is acceptable and expected.

## Architecture

```
Colleague is on the SIGC MUNIC 2026 report page (already logged in)
        │
        ▼  clicks the extension's button
  [1] POST AtualizarCriticas          (optional trigger; see below)
  [2] POST RelSituacaoMunicipioDados  -> HTML
  [3] DOMParser -> rows
  [4] validate; compare against current state in IndexedDB
  [5] write SCD type-2 snapshot
  [6] auto-download dated JSON snapshot  (durability, see below)
  [7] render the report panel
```

No network except to SIGC's own host. No background service worker polling.
Everything happens on an explicit click, matching `sigc-pro`'s established
posture.

### Modules

| File | Responsibility |
|---|---|
| `common/munic-common.js` | copied helpers: `f5Prefix`, `fetchViaGateway`, `downloadFile`, `buildCsv` |
| `features/situacao-fetch/` | the POST, URL construction, HTML parsing |
| `features/situacao-store/` | IndexedDB schema, SCD type-2 write, queries |
| `features/situacao-report/` | the three-tab panel |
| `features/situacao-export/` | JSON snapshot, two CSV exports |

`situacao-fetch` is the only module a SIGC change can invalidate.

## Endpoints

Confirmed against live 2026 traffic. Backend host:
`w3sigcmunic2026.ibge.gov.br`.

Both are POSTs sharing one body:

```
objJson={"IdUf":29,"IdAgencia":1,"IdMunicipio":0,"TipoQuestionario":0}
```

`IdAgencia:1` does **not** filter — observed responses span multiple agências.
`IdMunicipio:0` means all. `TipoQuestionario:0` means both questionnaires.
One request covers the UF.

`IdUf` is read from the page's `#IdUf` select, exactly as
`ultimo-movimento-export.js:getCurrentUf()` does (select2 hides the element
but keeps `.value` readable). No UF is hardcoded.

### URL construction

Reuse `f5Prefix(location.pathname)` and the dual-shape fallback from
`ultimo-movimento-export.js:relatorioFiltrarUrl()` — try the simple prefixed
path, fall back to the fuller captured shape:

```
simple: {origin}{f5.prefix}/Relatorio/{action}
full:   {origin}{f5.prefix}/Relatorio/f5-h-$$/Relatorio/{action}
                             ?F5_origin={f5.hex}&F5CH=I
```

With no F5 prefix (intranet), it is `{origin}/Relatorio/{action}`. The same
code covers both routes with no configuration — a significant simplification
over the previous design's explicit route handling.

URLs are built as **strings**; a query-param builder escapes `$$` and 404s.

### Headers

```
Content-Type:     application/x-www-form-urlencoded; charset=UTF-8
X-Requested-With: XMLHttpRequest
credentials:      same-origin
```

`X-Requested-With` is not decorative: these are ASP.NET MVC partial views and
commonly gate on `IsAjaxRequest()`. Matches `munic2025/R/sigc.R:39-52`.

### 1. `POST /Relatorio/AtualizarCriticas`

Triggers server-side recalculation of críticas. **Returns no content.**

**Default: off.** It mutates server state for the whole UF, the 2025 tool
never triggered anything, and if it is asynchronous a fixed wait yields stale
críticas with no error — wrong numbers presented as right. Exposed as a
separate, clearly-labelled button rather than folded into the main action.

To settle it: watch what SIGC's own UI does when the report page loads.

### 2. `POST /Relatorio/RelSituacaoMunicipioDados`

Returns HTML containing `table#tblMunicipios`. Parsed with `DOMParser` and
targeted **by ID** — the response also carries modal and DataTables markup.
`DOMParser` is inert; nothing in the fetched markup can load resources or run
handlers (the same guarantee `agenda-lookups` relies on).

| HTML column | Parsed fields |
|---|---|
| `UF` | `uf_sigla` |
| `Agência` — `"290070200 - ALAGOINHAS"` | `agencia_codigo`, `agencia_nome` |
| `Município` — `"2900702 - Alagoinhas"` | `municipio_codigo`, `municipio_nome` |
| `Questionário` | `questionario` — **new in 2026** |
| `Críticas Informativas` | `criticas_informativas` (`-` → 0) |
| `Críticas Comparativas` | `criticas_comparativas` (`-` → 0) |
| `Situação` | `situacao` |

### Change from 2025

2025 made one request per município for críticas
(`/Questionario/ObterCriticas?entidade={id}`, ~417 calls). 2026 needs **one**.
The fan-out, its throttling, and the `VerificarCriticas('\d+')` ID-scraping
regex are all deleted.

## Data model

**Primary key: `(municipio_codigo, questionario)`.**

2026 returns one row per município *per questionário* — `Básico` and
`Suplementar`, each with its own situação and críticas. 2025 assumed one row
per município: `process_situacao()` keys on `municipio_codigo` alone, and
every sheet's counts come from `get_relatorio_h()`'s `count()`
(`R/report.R:188`), which silently doubles under the new shape.

Questionário is a **first-class dimension**: it appears in every view, and
counts are per pair. This surfaces Suplementar lagging Básico, which any
collapsing scheme hides.

(`get_relatorio_sub()` would double too, but it is dead code —
`generate_report()` never calls it. Not ported.)

### Validation

Aborts before writing anything when the column set differs from expected, the
table is empty, or the key is not unique. A partial write that corrupts
history is worse than a failed run.

**Unknown `situacao` values pass through raw**, receive no colour, and are
named in a visible warning. The 2025 recode's `.default = "Supervisão/Análise"`
(`R/report.R:25`) would absorb a renamed status into the wrong bucket
unnoticed. Only `Não Iniciado` has been observed; the rest of the vocabulary
is unconfirmed.

| Raw (2025 vocabulary, a prior — not a guarantee) | Bucket |
|---|---|
| `Não Iniciado` | Não Iniciado |
| `Dig. Informante`, `Dig. Ibge`, `Em Validação` | Digitação/Validação |
| `Concluído` | Concluído |
| anything else | shown raw, flagged |

### Enrichment

The 2026 response already carries agência and município names, so joins serve
only **assistência grouping** and the **RCD 202531 reassignment**.

Two lookup tables ship as JS objects (following
`extension/common/municipios.js`, which already does exactly this):
agência→assistência, and the RCD reassignments. Generated from `orce` by a
committed script, not hand-maintained.

**Which agência is authoritative must be decided.** 2025 *discards* SIGC's
agência and takes it from `orce::agencias_bdo_mun` (`R/report.R:90-99`) before
applying the RCD. Default here: keep the 2025 behaviour, so year-on-year
comparisons stay meaningful. Flagged as an open question.

RCD 202531 is a 2025 administrative act, and the 2025 code carries an
undocumented 14-município exclusion list (`R/report.R:75-79`). Ported verbatim
behind a toggle; whether it still applies in 2026 is unconfirmed.

## Storage

**IndexedDB**, not `chrome.storage` — the latter has quota and structure
limits unsuited to a growing time series. Two object stores:

```
situacao   key: [municipio_codigo, questionario, from_ts]
           idx: current (until_ts = null), municipio, from_ts
runs       key: run_ts
           { run_ts, n_rows, n_changed, warnings, duration_ms }
```

SCD type-2, same semantics as the discarded DuckDB design:

- compare the fetch against rows where `until_ts` is null, keyed on
  `(municipio_codigo, questionario)`
- unchanged rows untouched; changed rows get `until_ts` stamped and a new row
  inserted
- **keys present in the store but absent from the fetch also get `until_ts`
  stamped** — otherwise a dropped município stays "current" forever and
  as-of reads lie

**Idempotence is required.** A second run minutes later must add no rows, or
the weekly view grows spurious columns. Comparison is on values, not run time.

**Every run appends to `runs`, including runs where nothing changed.** The
Município tab's columns are derived from `runs` (last run per ISO week), not
from distinct `from_ts`. Without this, a week where the tool ran but nothing
changed would have no column — indistinguishable from a week where nobody ran
it. 2025 could not make that distinction; here it is free.

**Timestamps are local (America/Sao_Paulo)**, matching 2025 (`R/report.R:111`).
ISO-week bucketing depends on this.

### Volume

~834 rows per run (417 municípios × 2 questionários). SCD type-2 stores only
changes, so steady-state growth is small; even daily full-change runs for a
year stay well within IndexedDB limits.

### Durability

IndexedDB lives in one browser profile on one machine, is invisible to the
author, and a cleared profile destroys it.

**Every run auto-downloads a dated JSON snapshot** (`munic2026_YYYY-MM-DD.json`)
to the Downloads folder. No prompt, no network. The colleague can copy it to a
shared drive; the author can import it for analysis in R; and history survives
a profile wipe without anyone remembering to export.

Import accepts these snapshots and merges by `(municipio_codigo, questionario,
from_ts)`, so histories from two machines can be reconciled.

## Report

A tabbed panel, following the MAPA-PRO pattern already established in
`ultimo-movimento-map.js` (Mapa / Zonas / Domicílios, sortable tables).

The 2025 workbook's five sheets collapse to **three tabs**, because counts and
percentages belong in one view rather than two:

| Tab | Content | 2025 equivalent |
|---|---|---|
| **Município** | one row per município × questionário; one column per week | `situacao_municipio` |
| **Assistência** | counts by assistência × situação × week, with % | sheets 2 + 3 |
| **Agência** | counts by assistência × agência, with % | sheets 4 + 5 |

Colours ported verbatim from `R/report.R:320-336`, as CSS classes:

| Situação | Font | Fill |
|---|---|---|
| Não Iniciado | `#9C0006` | `#FFC7CE` |
| Digitação/Validação | `#9C5700` | `#FFEB9C` |
| Supervisão/Análise | `#006100` | `#C6EFCE` |
| Concluído | `#0B77A0` | `#CAEEFB` |

Tables sortable by any column, as the existing Domicílios tab is.

### Weekly columns: last run of each ISO week

**The 2025 weekday-matching logic is deliberately NOT ported.**

`R/report.R:141-163` picks, per ISO week, the snapshot whose weekday is
closest to the most recent snapshot's weekday. That is built for near-daily
runs. **The 2026 run cadence is uncertain** — possibly weekly or irregular —
and under irregular runs the heuristic degrades in ways that are hard to
notice: a week represented by a Monday run sits beside a week represented by a
Friday run, as if comparable, and a skipped week disappears rather than
showing as a gap.

Instead: **one column per ISO week, taking the last run in that week.**
Well-defined for any cadence, needs no weekday matching, and is stable as runs
are added — a later run in the same week replaces the column rather than
shifting every other column's meaning.

Weeks with no run **appear as empty columns**, so gaps in monitoring are
visible rather than silently closed up.

Column headers show the week and the actual run date behind it
(`2026-W38 (18/09)`), so nobody mistakes a stale column for a fresh one.

### Export

Both CSVs are for **the author's analysis in R and for LibreOffice**, not for
the colleague's daily use — Excel Online cannot consume them, which is why the
panel carries the report.

- **JSON** — full history, auto-downloaded every run. The durability artifact.
- **CSV, denormalized** — one row per run per município × questionário, each a
  timestamped observation. Pivots trivially; no interval logic needed by the
  consumer.
- **CSV, state-change** — one row per state change with `from_ts`/`until_ts`,
  mirroring the store. Compact and exact, for analysis in R.

Both via the existing `buildCsv`/`downloadFile` helpers (`;`-separated, BOM,
Excel pt-BR compatible). Generating both from the same store is a few lines;
they are two buttons.

`.xlsx` via SheetJS is **deferred** — the panel plus these CSVs cover the
need, and conditional formatting through SheetJS is real work for an unclear
benefit.

## Permissions and privacy

```json
"permissions": ["storage", "downloads"],
"host_permissions": []
```

`storage` is for IndexedDB persistence; `downloads` for the snapshot. No
`host_permissions` — content scripts run on the SIGC origins and fetch
same-origin, as `sigc-pro` does.

The privacy text states plainly: MUNIC collection status is stored locally in
the browser and written to the Downloads folder; nothing is transmitted
anywhere except to SIGC's own server, on an explicit click.

`sigc-pro`'s own guarantee and CI gate are untouched by this project.

## Failure modes

Both return **HTTP 200**, so status checks miss them.

| Symptom | Meaning | Message |
|---|---|---|
| `type="password"` in body | session expired | "sua sessão expirou — recarregue a página e faça login" |
| `<title>Working` | F5 bounced to SSO | same |
| `#tblMunicipios` absent | error page or SIGC change | show what came back; abort |

Because the colleague is *on* the page when they click, an expired session is
both obvious and trivially fixed — a refresh. This is the single largest
operational advantage over every local-script design.

## Testing

Follows `sigc-pro`'s existing bun test setup. All run without a browser or a
live portal:

- **Parsing** — the live 2026 HTML sample captured during design is fixture #1
- **SCD type-2** — unchanged run adds nothing; changed value closes and opens;
  vanished key is closed
- **Weekly columns** — last run per ISO week; irregular cadence; two runs in
  one week collapse to one column; a week with no run yields an empty column
- **Validation** — missing column, empty table, duplicate key, unknown
  situação
- **URL construction** — F5 prefixed and bare, both shapes
- **Import/merge** — two overlapping snapshots reconcile without duplicates

## Open questions

1. Does RCD 202531 (and its 14-município exclusion list) still apply in 2026?
2. Is `orce` or SIGC authoritative for agência? (Default: orce, as in 2025.)
   If SIGC's own agência proves sufficient, both the enrichment tables and the
   RCD logic leave the MVP entirely.
3. Full `situacao` vocabulary — only `Não Iniciado` observed before collection
   started. Handled by flagging unknowns, not guessing.
4. Is `AtualizarCriticas` synchronous? Off in the MVP until known.
5. How often will this actually be run? The design no longer depends on the
   answer — weekly columns take the last run of each ISO week, whatever the
   cadence — but it determines whether a "one column per run" view is worth
   adding later.
6. Does the colleague's browser allow loading a second extension? `sigc-pro`
   is already in use, so the deployment path is presumably solved.

## Out of scope

- Any local runtime: Python, R, `.bat`, DuckDB
- Automating login of any kind — the colleague is already logged in
- Scheduled or unattended runs; every run is an explicit click
- UFs beyond the one selected on the page
- Per-município críticas detail beyond the counts in the situação table

## Review history

**Draft 1 reviewed 2026-09-22.** Found a fatal flaw in the Playwright session
model (Chromium's `os_crypt` cookie encryption is not Chrome-specific;
session cookies are dropped on profile reload), several wrong citation line
numbers, `get_relatorio_sub()` as dead code, and — most valuably — that F5
authorisation is per backend host and is created only when that screen is
opened in the browser (`pns.zonas/R/sigc_usuarios.R:20-25`), a required step
the draft's flow omitted.

**Redesigned as an extension** after the user observed that a cookie-based
approach was less invasive than driving a browser, and that an existing
extension (`sigc-pro`) already solved this class of problem. That extension's
`ultimo-movimento-export` feature — which itself replaced a standalone Python
script — is the direct precedent for this design.
